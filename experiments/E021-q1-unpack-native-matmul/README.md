# E021: native backend без полного TensorTranspose

## Вопрос

Можно ли сохранить Q1 во внешней памяти, распаковать его EVIS-ядром в virtual INT8 и передать в более быстрый штатный backend без `TensorTranspose`?

Проверены два представления одной и той же операции:

1. public `vxTensorMatrixMultiplyNode`;
2. `vxConvolutionLayer` с ядром 1×1, где IFM=K и OFM=M. Для единственной пространственной точки такая свёртка математически равна GEMV.

## MatrixMultiply

INT8 API принимает граф, но закрытый exporter пытается скомпилировать внутренний EVIS shader. Без настройки он не находит `cl_viv_vx_ext.h`. Запуск builder из официального каталога `SDK/vsimulator/include/CL` исправляет include, после чего exporter падает с segmentation fault. `VIV_VX_ENABLE_SHADER=0` падение не устраняет.

Это программный дефект/ограничение exporter, а не доказанное физическое ограничение VIP9000. NBG не создаётся, поэтому target-тест невозможен.

## Conv1x1

Этот обход экспортируется. В NBG есть только:

- `e020_q1_unpack_i8`;
- `ConvolutionLayer`.

Строки `TensorTranspose` нет. Четыре adversarial-набора `M16×K32` прошли golden побитово.

### Сравнение M1024×K128

| backend | golden | device | end-to-end | GMAC/s |
|---|---:|---:|---:|---:|
| E020a FullyConnected | exact | 339.232 мкс | 395.405 мкс | 0.386 |
| E021 Conv1x1 | exact | 574.869 мкс | 651.310 мкс | 0.228 |

Удаление transpose не ускорило малую форму: реализация Conv1x1 медленнее BatchGemm.

### Полная M1024×K5120

Conv1x1 также повреждает большой virtual INT8-тензор:

- расхождение начинается с zero-based выхода 104;
- повторяемость steady-state только 20/29;
- `device = 28.425 мс`;
- end-to-end `29.295 мс`.

Сбой почти на той же границе, что и FullyConnected (строка 102), хотя transpose отсутствует. Следовательно, главный ограничитель — размер/планирование virtual INT8-промежутка, а не только transpose.

## Измеренный безопасный тайл

Для FullyConnected проверен `M96×K5120`:

- expanded virtual tensor: `96 × 5120 = 491520` байт (480 КиБ);
- golden 96/96, стабильность 100/100;
- `device = 2.029 мс`;
- end-to-end `2.105 мс`;
- `0.242 GMAC/s`.

Чтобы покрыть M=1024, нужно 11 таких тайлов. Линейная нижняя оценка без дополнительной склейки результатов:

- device: `22.324 мс`;
- end-to-end: `23.158 мс`.

Это примерно в 1.66 раза медленнее уже измеренного E014 direct-packed EVIS пути (`~13.97 мс`). Поэтому семейство «распаковать Q1 в virtual INT8, затем вызвать штатный FC/Conv» отклонено как итоговая оптимизация Bonsai.

## Что это меняет в стратегии

NPU не бесполезен: мы доказали точную fused-цепочку и нашли практическую границу промежуточного буфера. Но ускорение требует не отдельного expanded tensor, а ядра, которое выполняет unpack и dot/reduce в одном проходе по packed Q1. Следующий кандидат должен оптимизировать E014 непосредственно:

- больше повторного использования активаций на несколько строк весов;
- парные MAC-инструкции (`DP16x2_b`) после точного lane-mapping golden;
- отсутствие materialized `±1` tensor;
- выдача только partial/final sums.

Raw-профили и сводка находятся в `results/`.
