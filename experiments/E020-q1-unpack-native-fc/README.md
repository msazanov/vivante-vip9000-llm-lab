# E020a: Q1 unpack в виртуальные INT8-веса и штатный FullyConnected

## Цель

Проверить не отдельный микрокернел, а нужный для Bonsai путь данных:

`packed Q1 во внешней памяти → EVIS unpack → virtual INT8 → штатный FC/MAC → INT8 output`.

Ключевое требование: развёрнутые веса не должны быть внешним входом NBG. Внешний граф принимает только упакованные Q1-веса и активацию.

## Термины

- **EVIS** — программируемая векторная часть VIP9000. Здесь она извлекает отдельные биты и превращает `0/1` в `-1/+1`.
- **Virtual tensor** — промежуточный тензор OpenVX, не объявленный входом или выходом графа. Планировщик может держать его во внутренней памяти NPU.
- **FullyConnected / BatchGemm** — штатная операция матричного умножения. В NBG также появился `TensorTranspose`.
- **Golden** — простой CPU-расчёт `sum(weight_i * activation_i)`, с которым побитово сравнивается NPU.
- **H2D** — передача входа host-to-device; **D2H** — чтение результата device-to-host; **run** — весь вызов исполнения через драйвер; **device** — время, которое сообщил профилировщик самого VIP9000.

## Что доказано

Vivante SDK 5.11.0 успешно принял выход custom EVIS node как виртуальный `VX_TYPE_INT8` тензор весов для `vxFullyConnectedLayer`. Получившийся NBG содержит строки операций:

- `e020_q1_unpack_i8`;
- `TensorTranspose`;
- `BatchGemm`.

На реальном VIP9000:

1. `M16×K32` — четыре adversarial-набора (`all zero bits`, `all one bits`, `0x55/0xaa`, смешанный) по 10 повторов каждый побитово совпали с golden.
2. `M1024×K128` — 1024/1024 выходов совпали, все 100 повторов стабильны.
3. Внешний размер весов для `M1024×K128` равен 16 KiB Q1 вместо 128 KiB развёрнутого INT8. В NBG нет внешнего expanded-weight input.

Это подтверждает, что физическое ограничение «одно NPU-ядро» не запрещает цепочку custom-op + native-op внутри одного NBG.

## Корректный профиль M1024×K128

Средние по 99 steady-state итерациям:

| участок | время |
|---|---:|
| H2D | 7.324 мкс |
| run | 378.800 мкс |
| D2H | 9.281 мкс |
| device | 339.232 мкс |
| H2D + run + D2H | 395.405 мкс |

Полезная арифметическая производительность всего fused-графа — около `0.386 GMAC/s`.

## Отрицательный результат M1024×K5120

На форме, близкой к одному большому GEMV Bonsai, монолитное разворачивание всех весов в virtual INT8 **не прошло golden**:

- первые 102 строки корректны;
- расхождение начинается с zero-based строки 102;
- только 25 из 29 steady-повторов дали одинаковый результат;
- `device = 25.910 мс`, end-to-end `26.473 мс`;
- это медленнее ранее измеренного E014 direct-packed пути около `13.97 мс` для той же формы.

Размер корректной части `102 × 5120 = 522240` байт очень близок к 512 KiB. Это сильная, но пока не окончательная улика в пользу предела/ошибки планирования большого виртуального буфера. Называть его подтверждённым физическим размером SRAM нельзя без пороговой серии.

Этот вариант отклонён: он одновременно теряет корректность и скорость.

## Практический вывод для Bonsai

Сам принцип работает и не требует раздувать Q1 во внешней памяти. Но разворачивать целую матрицу нельзя. Следующий вариант должен быть тайловым и избегать автоматически добавленного полного `TensorTranspose`:

1. распаковывать небольшой блок, гарантированно меньше найденной границы;
2. немедленно умножать его;
3. накапливать partial sums внутри NPU;
4. наружу отдавать только итоговый вектор;
5. отдельно проверить `vxTensorMatrixMultiplyNode`/Conv-представление, чтобы убрать дорогой transpose перед `BatchGemm`.

Пока это доказательство исполнимости гибридного Q1-графа, а не доказанное ускорение полного токена Bonsai.
