# E022: fused packed-Q1 dot/reduce для VIP9000

## Статус и цель

Это отдельная исследовательская ветка для A733/VIP9000. Цель — ускорить decode-инференс Bonsai без расширения Q1-весов в DDR и без дополнительной ошибки относительно текущего CPU golden.

Контрольная точка E014 уже выполняет точный `Q1_0 × Q8_0` через EVIS, но для большой проекции `M=1024, K=5120` занимает около 13.97 мс. E020/E021 доказали, что передача materialized virtual INT8-весов в FC/Conv технически возможна, но этот путь медленнее и ломается на больших промежуточных буферах. E022 возвращается к fused-вычислению: бит извлекается и участвует в dot-product сразу.

## Точный математический контракт

Для знака Q1 `s_i ∈ {-1,+1}` и бита `b_i ∈ {0,1}`, где `s_i=2b_i-1`:

```text
dot = Σ(s_i · q_i)
     = 2·Σ(b_i · q_i) - Σ(q_i)
```

`Σ(q_i)` вычисляется один раз для общего Q8-блока и переиспользуется всеми строками Q1. Expanded `-1/+1`-вектор не создаётся ни в DDR, ни в virtual tensor. Частичная сумма хранится в INT32; Q1/Q8 FP16 scales применяются один раз после завершения integer reduction.

Для canonical Q1_0×Q8_0:

```text
out = d1[row] · d8[block] · dot(row, block)
```

Порядок операций и округление должны совпадать с существующим E003/E014 golden. Допустимая ошибка — только уже наблюдаемая FP32/FP16 деквантизация, ориентир `max_abs ≈ 1.8e-7` на текущем fixture.

## Кандидаты

### A. Две обычные DP16x1 — базовый fused-вариант

EVIS извлекает по 8 бит, переводит их в `0/1`, выполняет `DP16x1(bits,q)` и отдельно `DP16x1(ones,q)`. Формула `2*selected-total` даёт точный dot.

Плюсы: уже подтверждённые uniform-конфигурации и lane-order; минимальный риск компилятора.

Минусы: больше DP-вызовов, чем у парной инструкции.

### B. DP16x2_b для двух строк

Один Q8-блок подаётся в парную инструкцию вместе с двумя Q1 bit-векторами. Это уменьшает число DP-инструкций приблизительно на 40% для K=128, но SDK не документирует точный x/y lane mapping `DP16x2_b`.

Правило эксперимента: сначала отдельный 4-выходной probe `[pair.x,pair.y,ref_hi,ref_lo]` на сырых векторах. Только после bit-exact mapping разрешается встраивать инструкцию в Q1 kernel.

### C. Упакованные nibble/LUT-суммы

Заранее считать для каждого Q8-байта четыре возможных знаковых вклада и индексировать их nibble-маской. Это может сократить BitExtract, но требует либо таблиц, либо EVIS gather, которые не подтверждены для VIP9000. Кандидат остаётся теоретическим и включается только при отсутствии результата у A/B.

Рекомендуемый порядок: A как безопасный baseline, затем B как основной speed-кандидат, C — только как отдельный negative gate.

## Архитектура NBG

Один custom EVIS SH node принимает canonical packed Q1 и Q8 carrier. Он читает только текущий tile, удерживает знаки/активации в регистрах и пишет маленький partial-output tensor. Второй node либо выполняет следующий reduction tile, либо передаёт partial sums в уже проверенный host-side FP32 reducer. В production-кандидате внешний граф не получает expanded weight tensor.

Для первой target-проверки сохраняется один custom node и форма `M=16,K=128`, чтобы изолировать lane mapping. После golden расширяем до `M=1024,K=5120` с четырьмя строками на work-item, как в E014. Температура, cycles, device/run/H2D/D2H и repeat_equal обязательны для каждого запуска.

## Ворота качества

1. CPU algebra test: случайные, all-zero, all-one, `0x55/0xaa`, знакопеременные Q8 и крайние INT8 `{-128,-127,-1,0,1,126,127}`.
2. Host compiler gate: NBG ненулевого размера, без expanded graph input.
3. Target golden: bit-exact integer dots и FP tolerance после scale.
4. Стабильность: минимум 100 повторов, `repeat_equal=100/100`.
5. Performance gate: сравнение с E014 на одной плате, при зафиксированной температуре и частоте NPU.

Кандидат считается ускорением только если он точен и уменьшает end-to-end время большой `M1024×K5120` проекции ниже 13.97 мс. Иначе результат фиксируется как отрицательный, но сохраняется для архитектурной базы.

## Риски и защита от ложных выводов

- `DP16x2_b` может иметь неожиданный lane mapping; это проверяется отдельным raw probe, а не выводится из документации.
- EVIS shader может писать только ограниченный формат/ширину; write-back делается частями, без записи expanded weights.
- FP16 scale carrier нельзя reinterpret-ить без target golden; до такого теста scale читается typed image.
- Низкое H2D не означает высокую производительность: основной показатель — device и end-to-end на полном GEMV.
- Любой mismatch на полном размере блокирует speed claim, даже если micro-test быстрый.
